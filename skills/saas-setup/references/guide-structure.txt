Deployables

apps/main and apps/api are two independent Cloudflare Workers. See
guide-split-workers.md for the full contract.

  example.app       apps/main   TanStack Start, default server entry
  api.example.app   apps/api   Hono, Better Auth, every binding and secret
  blog.example.app  apps/blog  (planned) static blog, see guide-blog.md

The web Worker never touches the database, R2, queues, or secrets. Every API
call — from the browser or from SSR — goes to the api origin over HTTP. SSR
forwards the incoming cookie; the session cookie is shared across subdomains
via Better Auth crossSubDomainCookies.

Dependency direction

  apps/main  → packages/shared, packages/ui, packages/icons
              apps/api (import type only — AppType for hc)
  apps/api  → packages/db, packages/shared
  packages/ui    → packages/icons
  packages/db    → packages/shared (optional, for enums/types)
  apps/blog → packages/ui, packages/icons (optional, if its tool can use them)
  packages/shared → nothing in the workspace

Nothing imports from an app except apps/main's type-only import of AppType.
apps/main links to the blog by URL only.

Route surfaces

Root-level routes are the public site: server-rendered on every request,
indexable. Nothing is prerendered: static assets are served by path on every
host, so a prerendered page would shadow tenant paths (see the Hosts section of
guide-route.md for the options).

admin.tsx and everything under admin/ are the product. The layout route owns the
product head (noindex, viewport, theme-color, webmanifest), the
pending/error/not-found boundaries, and the product root layout. A product route
inherits all of it by living under admin/. SSR stays on; protected routes read the
session in beforeLoad through lib/auth/session.ts.

The /admin prefix is the internal namespace and the route ID. What the browser
shows for it is a deployment concern owned by lib/routing/, which can map the
product namespace onto the root of a dedicated host. Always link and navigate
with the internal /admin path and let that module rewrite the public URL.

Structure rules

1. Route files stay thin and delegate behavior to pages, screens, features,
   components, or lib.
2. TanStack generates each createFileRoute path ID from its filename. Never edit
   that string by hand; let the route plugin update it after a deliberate rename.
3. A feature owns domain-specific product UI, queries, handlers, state, and
   types. Add a subdirectory only when it contains real code.
4. pages/ holds public marketing pages: public, copy from JSON, same HTML for
   every visitor. Marketing code never goes in features/. A page's UI and icons
   come only from its own folder or packages/ui; it may import a feature hook
   for an interactive island, and never imports another page. See
   setups/guide-pages.md. The blog is not a page: it is a separate static app
   (apps/blog), see setups/guide-blog.md.
5. components/ contains application UI shared across features and pages.
   Reusable primitives independent of the app belong in packages/ui.
6. lib/ contains cross-feature framework and infrastructure modules.
7. apps/main has no server code that touches data. A server function in web may
   only call the api (forwarding the cookie), never a binding or the database.
8. packages/db is imported only by apps/api. An Oxlint no-restricted-imports rule in
   apps/main bans it, and bans value imports from apps/api.
9. packages/shared holds code both apps need at runtime — zod schemas, shared
   types, constants. It has no framework, DB, or Worker dependencies.
10. Icons are imported only from packages/icons, never from the icon library
    directly, so the set stays in one place.
11. Extract a new package only when it has a clear boundary (runtime split, or a
    second consumer). Do not create pass-through packages for symmetry.

Backend structure rules (apps/api)

1. A feature owns its routes, its service, and any module only it uses. Files
   are named <feature>.route.ts, <feature>.service.ts, and <name>.queue.ts; a
   feature with more than one sub-app adds <name>.route.ts.
2. A route file is a Hono sub-app with its handlers written inline after the
   path — no controllers, so Hono infers the types that hc<AppType> relies on.
   Validate with zValidator; auth with middleware/auth.ts.
3. A service holds the DB and business operations that more than one caller
   needs, or that must be atomic (conditional UPDATEs, locking transactions).
   It takes `db` / `env` as arguments and never touches the Hono context.
   Handler-local helpers stay in the route file.
4. A feature may import another feature's service. Keep that graph one-way; a
   cycle means the function belongs in the other feature.
5. Queue consumers live with their domain as *.queue.ts and export the message
   type, the producer, and the batch handler. Cron work is exported service
   functions. index.ts only dispatches by queue name or cron expression.
6. integrations/ wraps an external provider behind a provider-neutral
   interface; switching providers touches only that folder.
7. lib/ is cross-feature infrastructure. Domain logic never goes there.
8. app.ts registers CORS (explicit web origin,
   credentials: true) before everything, then mounts Better Auth at /auth/*
   and the feature routers. Hono reads the session only through
   middleware/auth.ts.
9. app.ts exports AppType. apps/main/src/lib/client.ts is the only web file that
   may import it, type-only.
